# open-hard-ideas

> 「こんなハードウェアがあったらいいな」を、Issueとして投げて育てる場所。

このリポジトリは、ハードウェア製品のアイデアを集め、  
**アイデア → 簡易設計 → シミュレーション確認** の段階まで育てるためのリポジトリです。

完成品を販売したり、実機試作まで必ず行ったりすることは目的にしていません。  
まずは「これ、作れたら便利では？」を気軽に残すことを重視します。

## How it works

基本単位は **1 Issue = 1つのハードウェア案** です。

Issueには、その案が現在どこまで検討されているかを表す Level を付けます。

| Level | 状態 | 目安 |
| --- | --- | --- |
| **Lv1 — Idea** | 単なる案 | 何を作りたいか、何に使うかが説明されている |
| **Lv2 — Design** | 簡単な設計図付き | ブロック図・回路図・主要部品・I/O・電源など、実装方法の概要がある |
| **Lv3 — Open Simulation Verified** | シミュレーション上で動作確認済み | 設計に対するシミュレーションまたはテストがあり、期待する動作を確認できる |

Level は「目標」ではなく、**現在到達している最高レベル** を表します。

### Lv1 — Idea

まずはここから始めます。

最低限、次の内容があれば十分です。

- 何を作りたいか
- 何に使いたいか
- おおまかな入力 / 出力
- 既存製品では何が足りないのか

この段階では、実現可能性が未確認でも構いません。

### Lv2 — Design

アイデアに対して、実装方法がある程度具体化した状態です。

例:

- ブロック図
- 簡易回路図
- 主要部品の候補
- コネクタ / I/O
- 電源構成
- 必要なプロトコルや変換処理
- 重要な制約や未解決事項

完全な製造データである必要はありません。

### Lv3 — Open Simulation Verified

設計したものが、シミュレーション上で期待通り動くことを確認した状態です。

可能であれば、次の情報も残します。

- 使用したシミュレータ / ツール
- テスト条件
- 再現方法
- テストベンチ
- 波形やログなどの結果
- 確認できていない事項

**Lv3 は実機での動作保証を意味しません。**

実機試作や量産設計まで進めたくなった場合は、このリポジトリの責務を超えた次の段階として扱います。

## Simulation policy

Lv3 の検証は、**オープンソースのシミュレーション環境で第三者が再現できること**を原則とします。

シミュレーション環境は、次の優先順位で選びます。

1. 用途に適した既存の OSS シミュレータを使う
2. 足りないデバイスモデル、BFM、アダプタ、テストベンチだけを追加する
3. 既存 OSS では表現できない場合に限り、必要なシミュレータやモデルを新しく作る
4. プロプライエタリな EDA ツールは、補助的な検証には利用できるが Lv3 の必須条件にはしない

すべてのハードウェア案を1種類のシミュレータで扱う必要はありません。  
検証対象の層に応じて、適切なツールを組み合わせます。

例:

| 対象 | OSS の候補 |
| --- | --- |
| FPGA / RTL / デジタル回路 | Verilator + cocotb |
| 軽量な Verilog 検証 | Icarus Verilog + cocotb |
| アナログ / 電源 / トランジスタ回路 | ngspice |
| MCU / SoC / Firmware を含む検証 | Renode |
| OS / PC / 仮想デバイスとの接続 | QEMU |

上記は固定ではありません。  
その案の検証により適した OSS がある場合は、そちらを優先します。

### Missing models

USB、SATA、PCIe、各種センサ、特殊なバスなど、必要な相手側モデルが存在しない場合は、  
シミュレータ本体を作り直すのではなく、まず既存のシミュレーション環境上で動くモデルを追加します。

たとえば cocotb 上で、

- Host / Device BFM
- Block device model
- Protocol responder
- Fault / error injection
- Reference model

などを作り、複数のハードウェア案から再利用できる形にすることを推奨します。

### Lv3 reproducibility

Lv3 へ上げる場合、可能な限り次のような構成で検証環境を残します。

```text
simulation/
├── README.md
├── run.sh / Makefile
├── tests/
├── models/
└── requirements.txt / pyproject.toml
```

理想的には、

```bash
cd simulation
./run.sh
```

のような少ない手順でテストを実行でき、**PASS / FAIL が明確に分かること**を目標とします。

さらに可能であれば GitHub Actions などの CI で自動実行し、

> Lv3 = 過去に一度動いた

ではなく、

> **Lv3 = 現在の main ブランチでも再現可能なシミュレーションが通っている**

状態を維持します。

## Issue workflow

1. 欲しいハードウェアを Issue にする
2. 最初は原則として Lv1 を付ける
3. 調査や議論で設計が固まったら Lv2 に上げる
4. シミュレーションで確認できたら Lv3 に上げる
5. Level が上がったら、古い Level と入れ替える

Level 用ラベルは、たとえば以下を想定しています。

- `level:1-idea`
- `level:2-design`
- `level:3-sim-verified`

1つの案には、原則として Level ラベルを1つだけ付けます。

## Writing an idea

形式は自由ですが、迷った場合は以下を使ってください。

```md
# Summary

何が欲しいか。

## Use case

何に使うのか。
誰の、どんな不便を解決するのか。

## Interface

入力 / 出力、コネクタ、電源など。

## Expected behavior

どう動いてほしいか。

## Why

既存製品や既存方式では何が足りないのか。

## Open questions

まだ分からないこと、調査が必要なこと。
```

Lv1では、すべて埋める必要はありません。

## Design files

Lv1の間は Issue だけで完結して構いません。

Lv2以降で設計データが増えてきた場合は、必要に応じて次のような形でリポジトリに追加します。

```text
designs/
  <issue-number>-<name>/
    README.md
    schematic/
    simulation/
```

Issueを議論の中心にして、リポジトリ側には再利用・再現したい成果物を置きます。

## Example idea

### USB Mass Storage → SATA Device Bridge

一般的な SATA → USB 変換とは逆方向に、

```text
USB Mass Storage
       ↓
    USB Host
       ↓
 Block Bridge
       ↓
   SATA Device
       ↓
    SATA Host
```

という変換を行うアダプタ。

たとえば、USBメモリに入れたテスト環境をノートPCのSATAポートから起動し、  
SSD/HDDを毎回用意せずにPCの動作確認をしやすくする用途を想定します。

このような、**「ありそうで無い」「逆向きならある」「ニッチだけど欲しい」ハードウェア案** を歓迎します。

## Scope

このリポジトリで扱うもの:

- ハードウェア製品のアイデア
- 回路・基板・FPGAなどの簡易設計
- インターフェース変換
- 組み込み機器
- 検証用・修理用・開発用の特殊な道具
- シミュレーションによる成立性確認

このリポジトリだけでは必須にしないもの:

- 実機試作
- 筐体の完成
- 認証取得
- 量産設計
- 販売・サポート
